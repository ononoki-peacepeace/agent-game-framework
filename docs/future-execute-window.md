# Future execution preserves the requested date and time window

Parent `0445cb8`, product `8d02f82`. EXECUTE_FUTURE selected due intentions only by recipient, ignoring the requested time window. A morning execution could therefore run the only due afternoon intention; explicit afternoon execution became ambiguous alongside an unrelated any-time intention. Direct baseline: 2 failures, 1 true-ambiguity control.

The executor filters by the explicit window. Expanding to original-language inputs then exposed the fast planner discarding both window and day offset (3 new failing cases, with the prior 3 cases passing after the executor repair). The planner now preserves those existing temporal fields while keeping execution scope `now`; the executor also checks an explicit nonzero day offset. An explicit tomorrow request cannot consume today's due intention. Unspecified windows remain ambiguous rather than guessed; an original any-time intention is not silently narrowed to afternoon.

`tests/future-execute-window.test.ts` covers those cases plus an actual JsonStore/new-service path: the original Chinese afternoon request executes one TALK, completes only afternoon and leaves the any-time intention due. A later new service receives the same request ID with refreshed revision and performs zero generation, leaving world bytes unchanged. Controlled offline interpretation/narration is evidence for original-language fast-plan binding and actual settlement/replay, not a claim of broad Semantic model understanding.
