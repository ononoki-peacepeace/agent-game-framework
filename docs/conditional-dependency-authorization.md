# Conditional dependency ownership

A dependency establishes execution order. It must not silently authorize a side effect when its condition is false or unknown. The previous validator accepted mutating goals that depended directly on a condition without a `then`/`else` guard. The executor could complete the condition node and still persist an unauthorized future intent. A branch with multiple direct condition parents also selected the first parent's result. A nested condition could drop its outer guard.

`assertConditionalOwnership` now checks the existing graph before plan admission and again before `executePlan` reads or mutates state. Mutating goals and nested condition nodes with a direct condition parent must name a branch; a branch must have exactly one direct condition owner. Ambiguous plans are rejected for correction, without choosing an AND/OR meaning. Read-only queries can still depend on evaluating a condition without acquiring mutation permission. Existing valid then/else and explicitly nested current evaluation remain intact. No action routing, keyword inference or public schema was added.
