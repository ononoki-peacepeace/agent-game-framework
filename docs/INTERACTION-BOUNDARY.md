# 交互边界：模型负责自然互动，程序只结算世界效果

这条边界是本框架的长期工程约束，不是某一轮的功能描述。

## 职责划分

**AI / Agent 负责**：理解玩家自然语言、运行普通场景、普通观察、普通交谈与社交互动、推理，并根据当前场景决定何时需要调用世界能力。普通互动（聊天、打招呼、问问题、开玩笑、试探、安慰、吵架、看一圈、听动静、敲门、根据眼前结果继续交流）**不需要**被预先枚举成 Action Type，也不要求每一句都走 `Goal → Action → binding → receipt → narrator` 全链。

**程序负责**：权威事实来源、权限与约束、状态验证、时间/地点/资源结算、持久化、receipt、防重复副作用、客观世界一致性。

模型可以产出自然叙事、NPC 回复、场景内即时且非权威的互动结果，以及**可选的效果提案（Effect Proposal）**；只有需要持久化的部分才进入程序验证与 commit。

## 必须程序化的变化（不得由文字宣称）

地点真正改变、世界时间推进、金钱、库存、物品所有权、门锁/破坏等持久物理状态、HP/伤势、死亡、正式新增或删除人物、持久关系变化、正式知识/记忆写入、长期状态变化、世界事件，以及任何会影响未来客观模拟的事实。

## Goal 与 Action 的关系

- **Semantic / Open Goal**：玩家的开放意图，允许保留为开放目标，由 Agent 分步推进：做当前必要的一步 → 读取真实世界结果 → 重新理解剩余目标 → 继续。
- **Executable World Action**：需要严格结算的世界能力。

不允许把开放意图强制预编译成 `MOVE + OBSERVE + IF + TALK` 这样的封闭 DSL；也不允许因为未来步骤尚不可知而提前失败。

## 新增 Action Type 的准入规则

> 新增 Action Type 前，必须证明该行为需要**权威程序验证、持久化、事务，或可供未来世界依赖的结构化效果**。

如果新增的目的只是"让系统理解一个自然语言动词"，则**禁止新增**。原则上不应出现 `JOKE / COMFORT / WAVE / LOOK / LISTEN / THINK / ASK / SMILE / SIGH / CHAT / WATCH / OBSERVE / KNOCK` 这类动作类型——它们首先属于 Agent 的场景运行能力。

## Action Registry 的定位

Action Registry **保留**，但它代表的是"需要程序严格结算的世界能力集合"（例如移动、购买、物品转移、使用物品、伤害、创建人物、设置世界状态），而不是"玩家可能行为全集"。这一区分必须体现在代码与 prompt 中。

## 玩家可见反馈

内部工程诊断（规划结构、绑定、契约、运行时引用等）**不得**作为玩家的主要反馈；内部原因写入日志，玩家侧给自然的世界内反馈。
